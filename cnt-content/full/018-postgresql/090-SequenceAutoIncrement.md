## 为什么自增主键绕不开序列

"给每行一个唯一编号"是主键的基本需求。PostgreSQL 的实现是一个**独立的计数器对象（SEQUENCE）**：`nextval()` 取值并前移，全局单调（每个会话取到的值不重复），因此自增列本质上都是"默认值调用 nextval"这一层语法糖。理解这一点，就能解释三个新手必然遇到的现象：

- **编号有空洞**：取值（nextval）不受事务回滚保护，`INSERT ... ROLLBACK` 后编号照样被消耗。这是设计而非 bug——若回滚要回收编号，并发事务就得互相等待，自增就失去意义；
- **并发下不严格递增**：默认缓存为 1 时全局递增，但不同会话取值有先后交错；调大 `CACHE` 后交错更明显；
- **编号不等于行数**：删除行不回收编号，`max(id) != count(*)` 是常态。

## 三种写法：SERIAL、IDENTITY、手动序列

```sql
-- 1. SERIAL：序列 + 默认值的语法糖（PG 特有, 非 SQL 标准）
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,          -- 等价于建 orders_id_seq + DEFAULT nextval()
    amount DECIMAL(10,2)
);

-- 2. IDENTITY：SQL 标准写法, PG 10+ 的官方推荐
CREATE TABLE users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- 拒绝手动指定 id
    name VARCHAR(100)
);
-- GENERATED ALWAYS     : 不允许手动插入 id（除非 OVERRIDING SYSTEM VALUE）
-- GENERATED BY DEFAULT : 允许手动插入, 不给就用序列
```

为什么推荐 IDENTITY 而不是 SERIAL：两者底层机制完全一样（都是序列），差异在语义边界——IDENTITY 把"这列由序列管理"写进列属性，`pg_dump` 恢复、权限（序列所有权）、行为都更明确；SERIAL 只是建表时的宏展开，事后容易被当成普通列对待。老资料教 SERIAL 是因为 IDENTITY 是 PG 10 才加入的。

```sql
-- 3. 手动序列：多个表共享一个号段、或需要跨库对齐编号时才需要
CREATE SEQUENCE order_seq START 1000 INCREMENT 1;
SELECT nextval('order_seq');
```

## 什么时候不用自增：ID 生成选型

| 方案 | 有序性 | 生成方 | 适用 |
| ---- | ------ | ------ | ---- |
| IDENTITY (BIGINT) | 全局单调 | 单库 | 无分布式诉求, 默认首选 |
| `uuidv7()` | 时间有序 | 任意节点 | 分布式/高写入, PG 18 内置 |
| `uuidv4()` / gen_random_uuid() | 无序 | 任意节点 | 兼容存量; 高写入下伤索引 |

选型判断：单库永远用 IDENTITY（体积小、索引友好）；多节点要独立生成 ID 时，PG 18 起直接用内置 `uuidv7()`——时间有序使插入集中在索引右侧，避开 `uuidv4()` 随机写放大的老问题（详见 [PostgreSQL 18 新特性](/postgresql/540-PostgreSQL18NewFeatures)）。早期资料推荐 ULID/雪花算法，那是因为当时 PG 没有内置有序 UUID，现在不再需要额外扩展。

## 序列函数与 DDL 速查

函数全部是**会话级**语义：currval 返回"本会话最近一次 nextval 的值"（未取过则报错），lastval 返回"本会话最近使用过的任一序列的值"。

| 函数 | 语义 |
| ---- | ---- |
| `nextval(seq)` | 取下一个值并前移（回滚不回收） |
| `currval(seq)` | 本会话最近一次 nextval 的值 |
| `setval(seq, v[, is_called])` | 设置当前值; is_called=false 表示"还没发出 v" |
| `lastval()` | 本会话最后使用的序列值 |

```sql
-- 查看序列定义（比 information_schema 更直观的是直接查序列对象）
SELECT * FROM order_seq;        -- last_value, log_cnt, is_called
SELECT sequence_name, start_value, increment
FROM information_schema.sequences
WHERE sequence_name = 'order_seq';

-- 建表后重置序列（导入数据/手动插入后对齐计数器）
ALTER TABLE users ALTER COLUMN id RESTART WITH 1000;
SELECT setval(pg_get_serial_sequence('users', 'id'),
              (SELECT max(id) FROM users));   -- 常用对齐套路

-- 修改属性 / 删除
ALTER SEQUENCE order_seq INCREMENT BY 2;
ALTER SEQUENCE order_seq OWNED BY orders.id;    -- 绑定到列: 删列时序列一起删
DROP SEQUENCE IF EXISTS order_seq;
```

## 坑点速览

- **setval 的 is_called 语义反直觉**：`setval(seq, 5000)`（is_called=true）表示 5000 已发出，下一次 nextval 给 5001；`setval(seq, 5000, false)` 表示下一次就给 5000；
- **currval 不报错的前提**：本会话必须先 nextval 过该序列，直接 currval 报 "currval of sequence is not yet defined"；
- **RESTART 只动计数器**：`ALTER SEQUENCE ... RESTART` 改的是下次取值起点，MAXVALUE/MINVALUE 等属性要单独 ALTER；
- **IDENTITY 覆盖插入**：`GENERATED ALWAYS` 下手动插 id 要写 `OVERRIDING SYSTEM VALUE`，否则报错——这是保护不是障碍。

### 任务一：解释一次"编号空洞"从哪来

需求：并发两个事务各插入一行，事务 A 回滚、事务 B 提交。表里最后两行的 id 是多少？中间的编号去哪了？如何让新导入的数据表的自增列从正确位置继续？

<details>
<summary>参考实现与讲解</summary>

两行 id 不连续（比如 1 和 3）：A 预取的 2 已随回滚被消耗，不会回收。这正是"nextval 不参与事务"的直接后果——若要回收，并发事务必须串行等待编号释放，得不偿失。导入数据后用 `SELECT setval(pg_get_serial_sequence('t','id'), (SELECT max(id) FROM t));` 对齐计数器；IDENTITY 列也可用 `ALTER TABLE t ALTER COLUMN id RESTART WITH <max+1>`。

</details>

### 任务二：SERIAL 与 IDENTITY 选一个并说出理由

需求：新建订单表，要求"不允许应用层指定 id"，并说明为什么不用 SERIAL。

<details>
<summary>参考实现与讲解</summary>

```sql
CREATE TABLE orders (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    ...
);
```
IDENTITY 的 ALWAYS 语义把"这列归序列管"升级为列级约束，手动指定会报错；SERIAL 只在建表时展开成 DEFAULT，事后任何有 INSERT 权限的语句都能塞 id，边界靠自觉。另外 IDENTITY 是 SQL 标准，迁移到其他数据库（DB2/Oracle 等）语法通用。

</details>

### 任务三：把一个"会话级"函数用对

需求：事务里连续 `nextval('order_seq')` 两次后执行 `currval('order_seq')` 和 `setval('order_seq', 5000)`，再 nextval 一次，三次"取值"分别是什么？换一个新连接直接 currval 会怎样？

<details>
<summary>参考实现与讲解</summary>

连续两次 nextval 得到 n、n+1；currval 返回 n+1（本会话最近一次取值）；setval(seq, 5000) 表示 5000 已发出；下一次 nextval 得到 5001。新连接直接 currval 报错 "is not yet defined"——currval/lastval 都是会话级状态，跨连接不可见，这也是并发下用 currval 代替 RETURNING 取新行 id 的隐患来源。

</details>

### 任务四：为什么高写入场景主键从 uuidv4 换成 uuidv7

需求：说明 uuidv4 在索引上的问题与 uuidv7 的解法；PG 18 之前要达到同样效果需要什么。

<details>
<summary>参考实现与讲解</summary>

uuidv4 完全随机，插入点分散在 B-tree 全树，页缓存命中率低、写放大明显。uuidv7 高位是毫秒时间戳，插入集中在索引最右端，append-only 写入模式。PG 18 之前需要 ULID 之类的外部生成（扩展或应用层）；18 起内置 `uuidv7()`，"要有序 UUID"不再需要装任何东西。分布式多写点场景同样适用，因为生成不依赖数据库。

</details>
