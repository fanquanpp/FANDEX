## 学习目标

读完本文你将能够：

1. 用「增长趋势」而不是「秒数」评价一段代码的性能；
2. 说出五级常见复杂度 O(1)/O(log n)/O(n)/O(n log n)/O(n²) 各自的增长画像与生活对照；
3. 给一段简单代码标出大 O，并用 timeit 实验验证自己的判断；
4. 理解为什么 n 变大 100 倍时，不同复杂度的差距是天壤之别。

预计 45 到 60 分钟，含两组计时实验。

## 1. 你现在要解决什么问题

同样「1 加到 100」：一个人从 1 加到 100 加了一百次，另一个人用高斯配对法 `(1+100) × 50` 一次算完。**结果相同，代价天差地别**。n=100 时你感觉不出来，n=1000 万时一个方案跑一晚、一个跑一瞬——写代码的人必须能在**写下的那一刻**就知道自己选的是哪种代价。大 O 记号就是这套「代价语言」。

## 2. 最小可运行实验：亲手计时

把两种加法写出来，用 timeit 计时（标准库自带，无需安装）：

```python
import timeit

def sum_loop(n):
    total = 0
    for i in range(1, n + 1):
        total = total + i
    return total

def sum_formula(n):
    return n * (n + 1) // 2

for n in (1000, 100000, 10000000):
    t1 = timeit.timeit(lambda: sum_loop(n), number=1)
    t2 = timeit.timeit(lambda: sum_formula(n), number=1)
    print(f"n={n:>9}  循环版 {t1:.4f}s  公式版 {t2:.6f}s")
```

预期输出（数字因机器而异，趋势一致）：

```text
n=     1000  循环版 0.0312s  公式版 0.000001s
n=   100000  循环版 3.1042s  公式版 0.000001s
n= 10000000  循环版 310.99s  公式版 0.000002s
```

读表：n 扩大 100 倍，循环版耗时也扩大约 100 倍（线性），公式版纹丝不动（常数）。**大 O 度量的就是这个「n 扩大时代价怎么涨」的趋势**——循环版是 O(n)，公式版是 O(1)。

## 3. 发生了什么：为什么只谈趋势

大 O 忽略常数与低阶项：`3n + 500` 记作 O(n)。因为 n 足够大时，常数与低阶项对趋势毫无影响——我们关心的是「n 上亿时它会不会要我的命」。判断口诀三步：

1. 只有常数步、不看输入 → O(1)；
2. 循环次数随 n 翻倍而翻倍 → O(n)；循环套循环（内层也随 n）→ O(n²)；
3. 每轮把问题规模砍半（二分）→ O(log n)；砍半后每层还要线性扫（归并/快排）→ O(n log n)。

## 4. 核心概念：五级阶梯与生活对照

| 复杂度 | n=1 千 | n=100 万 | 生活对照 |
| --- | --- | --- | --- |
| O(1) | 瞬间 | 瞬间 | 按学号在点名册直接翻页 |
| O(log n) | 瞬间 | 约 20 步 | 二分查字典（每页砍一半） |
| O(n) | 很快 | 约 1 秒 | 一页页翻完整本册 |
| O(n log n) | 快 | 约 20 秒 | 高效排序的代价 |
| O(n²) | 约 1 秒 | 约 12 天 | 每人与其余每人握手一次 |

两件事立刻可推：n=100 万时，O(n²) 与 O(n) 差着「天」与「秒」的量级；**把 O(n²) 降成 O(n log n) 或 O(n)，是算法工作的核心回报**。

## 5. 调试实录：判复杂度的两个常见误判

误判一：忽略隐藏的循环。`sum(arr2d)` 看似一行，若是双层列表求和，实际是 O(n²)（行 × 列）。规则：**每层「随 n 变化的循环」都相乘**。

误判二：把函数调用当免费。循环里调用的函数若自身是 O(n)，整体是 O(n²)——判复杂度要把调用栈里的循环都算进去。修正手段固定：写完代码先数循环层数，再用 timeit 抽查一次趋势。

## 6. 修改实验

1. 给 sum_loop 换成 `total = total + i` 的步长 2 版本（只加奇数）——预测复杂度是否变化（常数减半不改趋势），验证；
2. 把 n 拉到 2000 万，验证 O(n) 的「翻倍即翻倍」预测；
3. 用 timeit 对比 `1000000 in arr`（列表查找）与 `1000000 in s`（集合查找，先 `s = set(range(1000000))`）——体验 O(n) 与 O(1) 的日常差距，这也是「为什么有哈希表」的种子（070 篇）。

## 7. 小练习

预测题（先写答案再验证）：下面两段的复杂度各是多少？

```python
def a(arr):                 # arr 长 n
    return arr[0] + arr[-1]

def b(arr):
    for x in arr:
        for y in arr:
            if x == y: return True
    return False
```

修改题：把 O(n²) 的「找两数之和等于 target」暴力双循环，改用集合降到 O(n)（提示：边遍历边把「需要的另一半」存进集合），并用 n=100000 验证耗时变化。

修 Bug 题：同事抱怨「列表查重太慢」，代码是 `for x in arr: if arr.count(x) > 1`——指出复杂度并给出 O(n) 修法。

挑战题（不看提示）：写一段程序实测「O(log n) 的二分查找 vs O(n) 的线性查找」在 100 万有序数组中查找 100 万个不同目标的总耗时，输出对照表，并用本文的阶梯表解释结果。

## 8. 什么时候应该 / 不应该死磕复杂度

应该：数据量到万级以上、代码要在生产跑、或准备技术面试时——大 O 是通用沟通语言。

不应该：n 永远是个位数的小脚本（可读性优先）；拿大 O 否定一切常数优化（小数据上常数可能主导，实测说话）。
