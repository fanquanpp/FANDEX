## 1. 问题：论文终稿.doc、终稿2.doc、真的最终版.doc

毕业论文、设计稿、游戏策划案……你是不是也这样存过：

```text
论文/
  论文终稿.doc
  论文终稿2.doc
  论文终稿-真的最终版.doc
  论文终稿-真的最终版-导师批注.doc
  论文终稿-真的最终版-0903.doc
```

用复制文件夹硬扛版本，迟早撞上三堵墙：

- **哪个是最新的？** 文件名写日期靠自觉，拷错一份就是灾难；
- **改坏了想退回去？** 上一版被覆盖就永远没了；
- **两个人一起改？** 同学发来的「最新版」和你手里的「最新版」是两份不同的文件，谁对谁错只能人肉逐段比对。

这三堵墙，工程上有个专门的工具来拆，叫**版本控制系统（Version Control System，VCS）**。它把手工三件套自动化：

| 你手工做的 | 版本控制替你做的 |
| --- | --- |
| 复制整个文件夹改名「终稿2」 | 一条命令存一次快照，自动记下时间、作者、改了什么 |
| 翻回收站、找旧备份盘 | 随时回到任何一次快照，历史永久保留 |
| 微信传文件来回对版本 | 每人各自存快照，合并时自动对齐，冲突了明确指出哪一行打架 |

Git 是目前世界上使用最广的版本控制系统。你接下来要学的所有命令，都是在跟这张表的第二列打交道。

## 2. 动手：全篇唯一的实验

打开终端（Windows 用 Git Bash，macOS 用「终端」），输入：

```bash
git --version
```

预期输出（数字不必相同，以 `git version` 开头即成功）：

```text
git version 2.51.0
```

这条命令只回答一个问题：**Git 装好了没有**。它不进目录、不改文件，在哪个文件夹运行结果都一样。

如果输出是下面两种之一，说明系统找不到 `git` 这个程序：

```text
bash: git: command not found
```

```text
'git' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

定位方法见第 5 节；完整安装步骤在 [安装与配置](/git/020-GitInstallConfig)。本文到此不再引入任何新命令。

## 3. Git 与 GitHub：工具与网站

最常见的一句混淆：「我要学 GitHub」。先把关系钉死：

- **Git 是工具**：一个命令行程序，装在你的电脑上。它记账、存快照、回退历史，全程离线可用，没有账号概念。你敲的每一条 `git` 命令都发生在本机；
- **GitHub 是网站**：github.com，把 Git 仓库放到云端的托管平台，用来备份、展示和多人协作。同类还有 GitLab、Gitee，托管的都是同一件事——Git 仓库。

类比：Word 是工具，网盘是放文档的网站——没人问「Word 和网盘有什么区别」，Git 与 GitHub 同理。这决定了学习顺序：先学 Git（本模块），再到 GitHub 模块学「把仓库发上去、发起协作」。跳过 Git 直接学 GitHub，就像不会拍照先注册相册网站。

## 4. 三个词的最小解释

整个模块会出现几十个术语，但入门只需要先立住三个：

- **仓库（repository）**：一个被 Git 管理的文件夹。它 = 你的文件 + 一个隐藏的 `.git` 目录，后者是账本，记着全部历史。仓库可以在你电脑上，也可以在 GitHub 这类网站上；
- **工作区（working directory）**：仓库里你正在编辑的那些文件本体。你看到什么、改了什么，发生在工作区；
- **提交（commit）**：一次带署名、时间和说明文字的快照存档。仓库的历史就是一串提交连成的线：回到过去，就是回到某次提交时的样子。

三者关系一句话：**你在工作区改文件，攒一批有意义的改动做成一次提交，提交们排成仓库的历史。** 至于「提交之前」改动停在哪儿（暂存区），[基础操作](/git/050-GitBasicOperation) 与 [三棵树](/git/060-ThreeTrees) 会亲手带你撞见，此处不展开。

## 5. 常见错误与调试实录

第 2 节那两条报错，值得当成第一个调试案例：

1. 报错在说什么：系统想执行名为 `git` 的程序，但翻遍了 PATH 里登记的所有目录都没找到（PATH 机制见 [终端与命令行入门](/start/040-TerminalAndShellBasics)，更多排错在 [环境变量与 PATH](/shell/100-EnvVarPath)）；
2. 只有两种可能：**没装**，或者**装了但系统不知道**（刚装完没重开终端，旧窗口读不到新 PATH）；
3. 对症处理：重开终端再试；仍失败就回 [安装与配置](/git/020-GitInstallConfig) 重装，Windows 安装时确认勾选「添加到 PATH」。

PowerShell 用户看到的变体是：

```text
git : 无法将"git"项识别为 cmdlet、函数、脚本文件或可运行程序的名称。
```

同一个病因，换个说法而已。以后看到任何「command not found / 不是内部或外部命令」，都是这套三步。

## 6. 实际项目场景：FANDEX 自己就是活教材

你正在读的这套教程，来自一个叫 FANDEX 的仓库：装着网站端、桌面端、Android 端和全部教学内容的 monorepo，2900 多个纳入版本管理的文件、500 多次提交。三个可查证的事实：

1. 第一次提交在 2026 年 7 月 22 日，信息是 `feat: initialize FANDEX monorepo with web/desktop/android subprojects`——一个仓库的出生证明，一条可回溯的历史；
2. 提交信息有固定习惯：一行说清这回改了什么，前缀标类型——`feat:` 新功能、`fix:` 修 bug、`docs:` 改文档、`chore:` 杂务。半年后翻历史，不用打开内容就知道当时在干嘛；
3. 每次合入前都有独立分支与审查记录——这靠手工文件夹根本做不到。

你写课程作业、个人项目，用同样的循环（改文件、存快照、说明写清楚）就能享受到同款能力。这不是大厂专属，是每个写代码的人的日常。

## 本章总结

版本控制把「复制文件夹改名」的三堵墙拆成自动化：快照存档、任意回退、协作合并。Git 是本机工具，GitHub 是放仓库的网站，先学前者的命令再学后者的协作。仓库是「文件 + 账本」，工作区是你正在改的文件，提交是带署名的快照——这三个词是后面所有章节的地基。
