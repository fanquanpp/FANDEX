## 1. 12-Factor 概述

### 1.1 起源

12-Factor App 由 Heroku 联合创始人 Adam Wiggins 于 2011 年提出，是构建 SaaS 应用的方法论。

它的出发点是一个当时的观察：应用「上不了云」的根因通常不是技术，而是
代码与环境的纠缠——配置写死在代码里、状态存在本地磁盘、依赖系统全局
环境。十二个要素逐条拆解这些纠缠，让应用可以**被平台自动化地部署、
伸缩与替换**。读本文时建议带着判断句式：「这条要素保证了平台的哪种
自动化能力？」——比背诵条文有用得多。

### 1.2 核心目标

- 可移植性
- 云原生部署
- 持续部署
- 弹性伸缩

## 2. 十二个要素

### 2.1 Codebase — 代码库

一份代码库，多次部署。

```
一个应用 → 一个 Git 仓库
同一代码库 → 多个部署（dev/staging/prod）
不同应用 → 不同代码库
```

| 规则       | 描述                 |
| ---------- | -------------------- |
| 单一代码库 | 一个应用一个仓库     |
| 多次部署   | 共享代码，不同配置   |
| 不共享代码 | 不同应用不共享代码库 |

### 2.2 Dependencies — 依赖

显式声明并隔离依赖。

```json
// package.json
{
  "dependencies": {
    "express": "^4.18.0",
    "lodash": "^4.17.21"
  }
}
```

| 规则     | 描述             |
| -------- | ---------------- |
| 显式声明 | 通过清单文件声明 |
| 隔离     | 不依赖系统级包   |
| 锁定     | 使用 lock 文件   |

### 2.3 Config — 配置

在环境中存储配置。

```bash
# 环境变量
export DATABASE_URL=postgres://user:pass@host:5432/db
export API_KEY=sk-xxx
export LOG_LEVEL=info
```

| 规则     | 描述             |
| -------- | ---------------- |
| 不硬编码 | 配置不写在代码中 |
| 环境变量 | 通过 env 传入    |
| 严格分离 | 代码与配置独立   |

**配置判断标准**：在不同部署间是否变化？变化 → 配置，不变 → 代码。

### 2.4 Backing Services — 后端服务

将后端服务当作附加资源。

```
应用 ←→ 数据库（可替换）
应用 ←→ 消息队列（可替换）
应用 ←→ 缓存（可替换）
```

| 规则     | 描述                 |
| -------- | -------------------- |
| 统一接口 | 本地和远程服务无差别 |
| 可替换   | 通过配置切换服务     |
| 松耦合   | 不绑定特定实现       |

### 2.5 Build, Release, Run — 构建/发布/运行

严格分离构建和运行阶段。

```
构建：代码 → 可执行包
发布：可执行包 + 配置 → 发布版本
运行：启动发布版本
```

| 阶段    | 输入        | 输出     |
| ------- | ----------- | -------- |
| Build   | 代码 + 依赖 | 构建产物 |
| Release | 构建 + 配置 | 发布版本 |
| Run     | 发布版本    | 运行进程 |

### 2.6 Processes — 进程

以无状态进程运行应用。

| 规则     | 描述               |
| -------- | ------------------ |
| 无状态   | 进程不存储状态     |
| 持久数据 | 存入后端服务       |
| 可替换   | 任何进程可随时停止 |

### 2.7 Port Binding — 端口绑定

通过端口绑定提供服务。

```javascript
// 应用自包含 Web 服务器
const server = app.listen(process.env.PORT || 3000);
```

| 规则     | 描述                  |
| -------- | --------------------- |
| 自包含   | 不依赖外部 Web 服务器 |
| 端口监听 | 通过端口暴露服务      |
| 可寻址   | URL 即服务            |

### 2.8 Concurrency — 并发

通过进程模型进行扩展。

```
扩展方式：
- 横向扩展（增加进程数）
- 纵向扩展（增加资源）
```

| 进程类型 | 描述           |
| -------- | -------------- |
| Web      | 处理 HTTP 请求 |
| Worker   | 处理后台任务   |
| Clock    | 定时任务       |

### 2.9 Disposability — 易处理

快速启动和优雅终止。

| 规则     | 描述                 |
| -------- | -------------------- |
| 快速启动 | 秒级启动             |
| 优雅关闭 | 处理完当前请求后退出 |
| 健壮性   | 进程可随时被替换     |

```javascript
// 优雅关闭
process.on('SIGTERM', () => {
  server.close(() => {
    process.exit(0);
  });
});
```

### 2.10 Dev/Prod Parity — 开发/生产一致

尽可能保持开发、预发布和生产环境一致。

| 差异 | 传统 | 12-Factor |
| ---- | ---- | --------- |
| 时间 | 数周 | 数小时    |
| 人员 | 不同 | 相同      |
| 工具 | 不同 | 相同      |

### 2.11 Logs — 日志

将日志视为事件流。

```bash
# 输出到 stdout/stderr
console.log("Request processed");
console.error("Database connection failed");
```

| 规则       | 描述               |
| ---------- | ------------------ |
| 不管理日志 | 应用不关心日志存储 |
| 事件流     | 日志是连续的事件流 |
| 集中处理   | 由外部系统收集     |

### 2.12 Admin Processes — 管理进程

将管理任务作为一次性进程运行。

```bash
# 一次性管理任务
rails db:migrate
python manage.py migrate
npx prisma migrate deploy
```

| 规则     | 描述               |
| -------- | ------------------ |
| 一次性   | 运行后退出         |
| 同代码库 | 使用相同代码和配置 |
| 同环境   | 在相同环境中运行   |

## 3. 现代扩展

### 3.1 超越 12-Factor

| 新要素    | 描述           |
| --------- | -------------- |
| API First | API 优先设计   |
| Telemetry | 遥测与可观测性 |
| Security  | 安全左移       |
| Container | 容器化         |
| CI/CD     | 持续集成部署   |

### 3.2 与云原生的关系

12-Factor 是云原生的理论基础，CNCF 的很多项目（Kubernetes、Istio）都是 12-Factor 的工程实现。

## 教学自检

遮住上面的表格与代码示例，先口头回答，再展开对照。答不出的回到对应要素重读：

1. 12-Factor 的出发点是「让平台具备哪种能力」？用这个句式检验 Config、Processes、Disposability 三条要素各保证了什么自动化。
2. 「一段字符串该进代码还是配置」的判断标准是什么？数据库连接串、接口 URL 常量、盐值各属于哪类？
3. Build/Release/Run 三阶段各自输入输出是什么？为什么说「构建时把配置烧进镜像」破坏了这个分离？
4. 后端服务（数据库/队列）当作「附加资源」意味着什么？换一个数据库实例时要改代码吗？
5. 优雅关闭要处理哪个信号？只靠平台强杀会丢什么？
6. 日志为什么该输出到 stdout 而不是自己写文件？谁来负责收集与存储？
7. 一次性管理进程（如数据库迁移）要与常驻进程共享什么？生产上运行它要防范什么？

<details>
<summary>参考答案（先答再看）</summary>

1. Config 保证环境间可移植（同一镜像跨 dev/staging/prod，只换环境变量）；Processes 保证实例可任意替换与水平伸缩（无状态所以随便杀随便加）；Disposability 保证快速启动与优雅终止，平台才能无感地重排、升级、缩容——共同支撑「被平台自动化地部署、伸缩与替换」。
2. 标准：部署环境之间会不会变。变 → 配置。数据库连接串每环境不同，是配置；接口 URL 常量是代码；盐值属于密钥类配置（进环境变量/密管，不进代码库）。
3. Build：代码+依赖 → 构建产物；Release：产物+配置 → 发布版本；Run：发布版本 → 进程。构建时烧配置意味着一个环境一个镜像，镜像不再「一次构建到处部署」，环境差异被提前冻结进了产物。
4. 附加资源 = 本地服务与远程服务无差别对待，全靠配置（URL）切换。换实例只改 DATABASE_URL，应用代码零改动——做到这一点才算解耦。
5. SIGTERM。处理完当前请求、关闭连接、把在途任务落盘或转交后再退出；平台强杀（超时后 SIGKILL）会丢在途请求与未持久化的状态。
6. 应用只管把日志当事件流写 stdout/stderr，不关心文件、轮转、留存；收集与存储是平台侧（采集器 + 集中式后端）的职责。自己写文件会让日志随容器一起消失，且与平台调度机制打架。
7. 共享同一代码库与配置（同构性保证迁移脚本与代码版本匹配）。生产要防误触发：迁移进程通常要求人工/流水线显式触发、加并发保护（避免两个实例同时迁移）。

</details>

## 小结

- 初学者要点：最有操作价值的三条是 **Config**（配置进环境变量）、
  **Processes**（进程无状态）、**Logs**（输出到 stdout 由平台收集）；
  判断标准永远是「部署环境之间会不会变」；十二条不是并列的清单，
  而是围绕「可替换的进程 + 可自动化的平台」这一个目标的展开。
- 进阶注意：12-Factor 写于容器普及之前，今天用容器 + 编排平台实现
  （镜像对应 Build、ConfigMap/Secret 对应 Config、探针与 SIGTERM 对应
  Disposability）；它也与现实有张力——日志有采样与结构化需求、管理
  进程在生产要防误触发、Dev/Prod 一致性受成本约束，工程上取「足够
  符合」而非教条；需要 15 条扩展版可参考社区「Beyond the Twelve-Factor
  App」（API 优先、遥测、认证授权等）。
